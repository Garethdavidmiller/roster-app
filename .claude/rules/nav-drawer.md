# The drawer, the page chrome and the overlay layer — area decisions

`nav-panel.js` (the drawer every app page shares), `about-lightbox.js` (the About panel and the
sub-page header logo) and `overlay.js` (every lightbox's lifecycle). These are their "never change
without discussion" decisions, moved here from `CLAUDE.md`'s architecture table. What binds every
page stayed there: every lightbox is built with `createLightbox`, a one-time notice opens through
`openNoticeIfClear`, and the page-chrome row (header logo, About, sign-out). The drawer's colours are
`css-tokens.md` → "Dark (navy) nav drawer + scoped tokens", which loads with any stylesheet.

| Decision | Rule |
|----------|------|
| The drawer on every app page | `nav-panel.js` injects overlay + drawer; burger `#navMenuBtn` in each page header. **THREE ZONES, ONE IDIOM EACH:** pills = go to a page · Latest = the documents you open on a shift · Reference = look something up. `NAV_PAGES` drives the pill row, `NAV_INFORMATION` the flat Workplace section, `NAV_GUIDES` the Reference submenu. **Four rules that have each been broken once** — the current page renders as an inert `aria-current` pill, NOT omitted · Settings is a pill, not a pinned link · pills are one per row · `aria-expanded` is the ONLY state for the Reference fold (no `.open` class — re-adding one re-creates the stuck-arrow bug). **The measurements and the argument behind all four are in `nav-panel.js`'s header.** Adding a guide = one `NAV_GUIDES` entry; adding a live doc = one `links` entry in `NAV_INFORMATION`; `comingSoon: true` renders a `<button>` opening `#navComingSoonLightbox`. |
| Pills a member may not open are filtered, not refused | `NAV_PAGES` flags `adminOnly` (Operations), `linksDesignerOnly` (Links), `overtimeAudienceOnly` (Overtime) and `newlinkAudienceOnly` (New link); `initNavPanel` filters on what each page passes (`isAdmin`, `isLinksDesigner`, `canOpenOvertime`, `canOpenNewlink`), and every coordinator passes all of them. Hiding a pill is not the boundary: each page guards itself — Operations, signed out, shows the shared in-place sign-in and sends a signed-in non-admin to `admin.html` (`operations-app.js`) — and the server refuses the rest. A gate here and its `auth-policy.js` role move together (`page-contract-parity.test.mjs`). Links: `links-design.md` → Access control. |
| Drawer head = About; it shows the version | The drawer head is a `#navPanelBrand` button (logo + title + `Version {APP_VERSION}` muted text). Tapping it closes the panel (`closePanel`) and calls `onLogoClick` once that close's Back echo has landed (`whenHistorySettled`), which each page passes as `() => openAboutLightbox?.()` — opening that page's `#iconLightbox`, built by `initAboutLightbox` (`about-lightbox.js`: version, update status, bug report, and page-specific print/guide links). A page stores the returned `.open`, never the returned object (the module header says what that cost). |
| Sub-page header logo = back to calendar | On every page but the Calendar the header logo `#appIcon` navigates to `./` (the app root — `./index.html` 301s on Firebase Hosting, a wasted round trip per tap), labelled "Back to calendar". One copy, `wireHeaderLogo` in `about-lightbox.js`; a page with unsaved work passes its own confirm-then-go. It restores an iOS-friendly back affordance (iOS standalone PWA has no system back) without re-adding a visible back button — kept "invisible" as just the logo. The **calendar page keeps its header logo opening About** (`.title-icon` in `calendar-app.js`) — home has no "back" target. Do not wire the calendar header logo to navigate. |
| No header back button | Sub-page headers carry no `←` back button — it duplicated the drawer's Calendar pill (two competing nav paradigms) and clashed visually with the logo box. Header is `[☰] [logo] Title … [badge]`. The admin "open calendar on the month I was editing" behaviour is on the `.nav-panel-pill--calendar` click in `admin-app.js`. `.btn-back` lives only in `guide-shell.css`. |
| Sign-out in the drawer footer | `initNavPanel({ onSignOut })` — each page passes its own sign-out callback (all of them go through `signOutAndLeave`, `page-session.js`). The footer (initials badge, member name and Sign out) renders only when `onSignOut` is supplied; `beforeSignOut` may cancel, and the push record is released only after it agrees. |
| Footer initials badge | A 26px circular badge (`#navPanelAvatar`) before the member name, always initials on a stable per-name colour. `avatarInitials(name)` and `avatarHue(name)` from `roster-data.js` are called directly in `nav-panel.js` — no fetch, no localStorage, no event listeners. The profile photo it replaced is removed; full spec and revert checklist in ROADMAP_HISTORY.md → "Removed features — full restoration specs". |
| Notification bell in the drawer footer | `nav-panel.js` renders a 🔔/🔕 toggle (signed-in only, hidden when `notifSupported()` is false — incl. iOS non-standalone); every line of push logic is `notif.js`'s, and the bell only renders and refreshes. Bell refreshes on every panel open; tap keeps the panel open. States: `on`/`off-default`/`off-lapsed`/`denied`/`unsupported`. The `#notifPrompt` calendar strip stays on the calendar; the Notifications card lives on settings.html. **The bell is a COMPACT icon next to Sign out (`.nav-panel-bell`)** — a labelled full-width "Notifications — On/Off" row has been tried and reverted TWICE (owner decision: the settings.html Notifications card is the canonical surface, the drawer bell is just a quick toggle). Don't re-promote it without a fresh discussion. |
| When a page wires its drawer | A page with a sign-in renders the drawer ONCE, with the signed-in identity: Settings defers `wireNavPanel()` to `initAuthorised()`, and the comment above `wireNavPanel` in `settings-app.js` says what restoring a module-scope call would re-create. Overtime wires it while signed out, on purpose, and its own comment says why. A signed-out visitor is not stranded — the login overlay carries its own "← Back to roster" (`login-overlay.js`). |
| App Notices archive | `nav-panel.js` owns it: `archiveNotice({ id, title, section, date, body })` writes to localStorage `myb_app_notices` (capped at 50 entries, deduped by `id`, entries older than `ARCHIVE_EXPIRY_DAYS` pruned on every write). "📣 App Notices" in the drawer's Reference zone opens the archive panel. The notices themselves live on their pages — `/new-notice`. |
| Android Back button overlay pattern | Overlays push `history.pushState({ mybOverlay: true })` when opening, close on `popstate`. `_pushOverlayState(handler)` / `_clearOverlayHistory()` are exported once from `overlay.js` and reached through `createLightbox`. The handlers are a LIFO stack, so nested overlays each get their own entry and Back closes only the topmost (`overlay.js` header). The drawer keeps its own entry, which its two lightboxes share — the reason they hand-roll their lifecycle. |
| Only the TOPMOST overlay reacts to the keyboard | Every open overlay attaches its own `document` keydown listener, so ONE Escape used to close them ALL — and `trapFocus` on a buried overlay pulled Tab into a dialog the user couldn't see. `createLightbox`'s `onKey` now returns unless `_isTopOverlay(close)` (reads the existing `_backHandlers` stack; **fails open**, because a suppressed Escape traps the user). Back and ✕ were always correct. **A one-time notice must open via `openNoticeIfClear(lightbox)`, never `lightbox.open()`** — with two notices up, one Escape ran both `onClose` callbacks, so the buried one was archived and flagged permanently seen by someone who never saw it. Not opening leaves it unflagged, so it returns next load. The rule is unit-tested; the WIRING needs the e2e (deleting the `onKey` guard leaves every unit test green). |
