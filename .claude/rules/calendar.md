# Calendar page — area decisions

The Calendar is `index.html` and the `calendar-*.js` modules. **What it may SHOW, and when, is the
contract `docs/CALENDAR_DATA.md`** — numbered invariants that other documents link rather than
restate. This file holds the page's own "never change without discussion" decisions. They moved here
from `CLAUDE.md`'s architecture table, which every session loads; the rows that bind more than this
page (access, `getBaseShift`, Christmas, Sundays, the hash-opened documents) stayed there.

| Decision | Rule |
|----------|------|
| `aria-live` for month announcements | Programmatic `.focus()` on the month heading caused mobile layout reflow. Do not switch. The announcer is `#ariaAnnouncer` in `index.html`. |
| `Math.ceil()` on carousel panel width | Eliminates sub-pixel seam on high-DPI screens. Do not remove (`calendar-swipe.js`, beside `gestureW`). |
| `_staleMemberName` in `calendar-member.js` (the BANNER is in `calendar-app.js`) | When `getSelectedMemberIndex()` can't find a saved name, sets flag, falls back to default member. On the next page open the banner fires via `_showStaleMemberBanner()` — called from the pre-branch init block for team-view users, or from inside `renderCalendar()` for calendar-view users. `takeStaleMemberName()` is one-shot so only one path fires. |
| Sync chip state machine in `calendar-initial-fetch.js` | hidden → (800ms) → "↻ Updating your shifts…" → silent remove on success, or "⚠ Couldn't update" (stays until a retry works; the deadline is `SYNC_TIMEOUT_MS`). A retry says "↻ Retrying…" for at most `RETRY_TIMEOUT_MS`, then hands the control back as a failed read does (owner, 10 Nov 2026) — the read is not cancelled, and a late answer still clears the chip. There is no "✓ Up to date" state — it was noise. Never show raw errors to staff. Hidden while the grid shows its OWN loading/failed panel (one message, not two); kept beside a failed panel that has no Try again, where it is the only retry. The panel's Try again withdraws a recorded failure (`dismissSyncError`), and so does a read confirming the month on screen (cal-data-5). |
| One-off notification prompt (`#notifPrompt`) | Appears once per device between `</nav>` and the swipe hint / calendar. Both Enable and × set `myb_notif_prompt_done` (`NOTIF_PROMPT_DONE` in `storage-keys.js`). Do not move below the calendar. It shares its slot with the install strip, which outranks it (`install-prompt.js`). If the system grants permission and the subscription still fails, the strip returns with its second line (`index.html`) instead of vanishing. |
| Team Week View | Available to everyone the Calendar admits (a signed-in member or the staff PIN); grade state (`currentTeamGrade`) persists across re-renders — it opens on the shown member's grade until the reader picks a tab, and a picked tab persists across re-opens — week nav clamped to `CONFIG.MIN_YEAR`/`MAX_YEAR`. **Overrides come from the SHARED month fetch** (`ensureOverridesCached`, injected), never a fetcher of its own: a second authoritative reconciler racing the first evicted overrides the 3-month fetch had just loaded, blanking the grid back to base roster. That is `CALENDAR_DATA.md` invariant 6, and the narrative behind it is in `calendar-overrides.js`. A month read Team View started lands with the coordinator's shared repaint (`onMonthRead`), so it repaints the Calendar if Team View has been left. **No override-load status indicator** — proposed by review and accepted as won't-do: a failed month releases from `fetchedMonths` (retryable) and leaves the last-good cache untouched, so a failed refresh keeps the last-good grid silently, which is the minimal-noise behaviour this app wants. (That is TEAM VIEW's answer and it stands: the MONTH grid labels a failed re-check "Saved copy — couldn't check for changes" — `CALENDAR_DATA.md` 18 — and Team View draws a saved-copy week exactly as a current one.) **The table's swipe hint shows only on touch AND only while the week is wider than its box** (`watchHintFit`, through `overflow-hint.js` — a ResizeObserver, shared with the Trains grid): on a tablet or a phone on its side the week fits, so there is nothing to swipe, and a change of size — a rotation clamping the box's scroll — is never taken for the member's swipe that retires it. **On a phone the names' box takes what the card leaves** (`flex: 1 1 0` with a half-screen floor, `index.css`), never a height worked out beside the card: v25.49's "screen less 250px" left an empty band wherever that sum was wrong, 82px on the owner's phone (v25.73). |
| **A calendar day opens the day panel — on EVERY pointer type** | Owner request: *"I want the day detail lightboxes like mobile on desktop."* The click handler in `calendar-renderer.js` has **no pointer branch** and must not regain one — its own comment says what it replaced and why. **The pay jump is not lost, it is one click deeper**, on the panel's `#dayDetailPayBtn`, which `personalActionsAllowed` already gates. **Three things that go with it and are easy to undo** — the hover tooltip stays as the preview and `body.lb-open #calTooltip` takes it down, a fine pointer gets `cursor: pointer` on a real day cell, and the KEYBOARD is deliberately unchanged (Enter still jumps from a pay cell and falls through to the panel when refused). Each is argued beside its rule in `index.css`, including which parts were MEASURED rather than assumed; `e2e/calendar.spec.js` pins the behaviour rather than the mechanism. |
| `navigateToPaycalc(paydayStr)` in `calendar-app.js` | The one route from a payday or cut-off cell to the calculator, carrying `?payday=`, and its one gate: `personalActionsAllowed`. Always call this helper — never duplicate the navigation logic. **It never diverts to a sign-in**: paycalc signs in in place and keeps the query, so a bounce through admin would only lose the date. The day panel's other action, `#dayDetailLeaveBtn` to Admin, is the same shape for the same reason. |
| **A change to the Calendar's state brings a test of the ORDER it could break** | External review, 10 Nov 2026. The Calendar's regressions have come from its state, and each was an order of events: a background re-check that failed left an old month drawn as current (v25.63, F1); an answer from an earlier access grant landed under the next one and was kept (F2); a retry waited for ever (v25.69). So a change to the access gate, the fetch claims, the month knowledge states or the local cache comes with a test that drives the sequence it could break (the late answer, the access lost mid-read, the retry after a failure) beside the happy path. Patterns to copy: "the exact reported sequence: A issued, B issued, B lands, A lands stale" (`calendar-overrides.test.mjs`) and "a late error cannot demote a month that has since succeeded" (`calendar-data-state.test.mjs`). **And `calendar-sequences.test.mjs` stays green** (11 Nov 2026): thousands of seeded random orders of those events through the real modules, eight rules checked after every one. A new event the Calendar can meet joins its `EVENTS`; a failure prints its seed — fix the code, never the seed list. Its first run found a fault the hand-written orders had missed. |
| **Whether a read's answer is still wanted is asked ONE way: its read ticket** | Calendar step 1, v25.72. Every override read takes `issueReadTicket()` as it is issued, and everything that handles its outcome (a success, a failure, either time limit, the cache's early paint) asks `answerStillWanted(ticket, err)` first: the same grant, not shut since, never `READ_SUPERSEDED`. The first load adds one question of its own, `standing` (has a newer attempt begun?), and one action for a no, `standDown`. **Never compare the grant number by hand again**: twelve hand-written checks became this one, and the bugs they produced were each a check asking half the question (v25.63 F1/F2; three failure paths and both time limits that ignored a lock until v25.72). A new path that handles an outcome asks the ticket and gets a test in "the read ticket" blocks of `calendar-overrides.test.mjs` / `calendar-initial-fetch.test.mjs`. |
| **Whether Calendar access is held is kept ONCE: `calendar-access-state.js`** | Calendar step 2, v25.74. The roster reads and the documents no longer hold a flag each; both ask the one state, which `calendar-access.js` writes (`grant`, `handleAccessLost`). **Never give anything a copy of its own, and never set a gate by hand from the page again**: the copies were each right, and the risk was the copying — a third way of losing access that shut one gate and forgot the other leaves this device's saved copy of everybody's leave readable behind the lock card, where no server rule looks. A new thing that must follow access READS the state or LISTENS to it; a new way of losing access calls `handleAccessLost` and nothing else. **Nor a second NAME for the write** (v25.76): each gate exported one for its older tests (`setOverrideAccess`, `setDocumentAccess`), and a second name reads as a narrower act than it is — "shut the documents" locked the whole Calendar. A gate reads; the roster gate's one write is a refused read shutting, and the document gate cannot write at all. Two orders hold it together and are easy to undo: a grant writes after the card has gone and BEFORE either hook, and a loss shuts BEFORE a card goes up. `calendar-access-state.test.mjs` counts every call of the write as written (a third writer, a call that is not a literal, or either old name coming back fails) and pins the page's wiring; the order tests are the last block of `calendar-access.test.mjs`. |
| **WHEN the Calendar page draws is decided in ONE place: `calendar-redraw.js`** | Calendar step 3, v25.75. The page file no longer keeps a variable per reminder: how far start-up has got, the wait for a swipe to finish, a change of name held behind it and the keyboard focus owed to the next grid are one scheduler, with the clock handed in so its rules run in a unit test. **Never give a deferred job a timer of its own in `calendar-app.js`, and never ask there whether a gesture is live (`isSwipeGestureActive`)**: a background repaint calls `redraw.repaint(why)`, the name picker `redraw.nameChanged()`, and a new job that must wait for the gesture joins the ONE wait. What that protects is the v16.23 freeze — a draw replaces `#calendarDisplay`, and the swipe's three panels live in it. A press the reader made still calls `renderCalendar` itself. `_repaintAfterMonthRead` stays one function with one identity, because a month read keeps its waiters by it. Start-up is `shell` → `workspace` → `surface`, forward only; two of its checks (`onEveryGrant`'s, and the ready metric's) are insurance no browser test can reach, pinned from the source. `calendar-redraw.test.mjs` fails when the page asks that question anywhere but the hand-over (its buttons and keys still read `isSwipeCooldown`, as before), and the `redraw:` tests in `e2e/calendar.spec.js` hold a finger down while a read lands and a name is picked. |

The day panel itself (`calendar-al-lightbox.js` and its `index.css` block) is in `CLAUDE.md` →
*Change impact*: it is the only place a member reads what a day is on touch, and its two shipped
defects were invisible to behaviour tests.
